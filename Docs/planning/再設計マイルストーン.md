# 3DSide 再設計マイルストーン

- 作成日: 2026-11-09
- ステータス: **計画案 v0.1**（工数・実装方式・完了時期は確定ではない）
- 想定稼働: 週10時間程度。各期間は目安であり、実測に応じて更新する。
- 最終目標: **ユーザーがプロットを渡すだけで、CodexのスキルとUnity側Builderが、手作業の配置なしにプレイ可能なステージを生成する。**
- 第一完成ライン: **グレーボックスで1ステージを最初から最後まで遊べること**。世界観に合わせた3Dアセット・装飾は別フェーズ。
- 重要: **AIにUnityコードと配置を一括で自由生成させない**。Skillが設計データを作り、Validatorが検査し、決定的なBuilderが配置する。

## マイルストーン一覧

| ID | マイルストーン | 期間目安（週10h程度） | 完了条件 |
|---|---|---:|---|
| M0 | 方針・既存資産の棚卸し | 1週間 | 残す/退役/作り直す境界を文書化し、作業ブランチと比較用Sceneを確保 |
| M1 | RailMotor基礎 | 3〜5週間 | 直線・曲線・ジャンプ・床/壁/天井衝突がレールXZ拘束を破らず動作 |
| M2 | 自然分岐 | 3〜6週間 | ジャンプ・落下による上下ルートの切替、合流・逆走がワープ/誤吸着なく動作 |
| M3 | ゲーム本体との接続 | 2〜4週間 | Player/Enemy、攻撃、アイテム、カメラ、死亡・リスポーンの最低限の回帰テストが通る |
| M4 | レベルデザインの計測・ルール化 | 1〜2週間 | ジャンプ距離・到達高度・安全余白・配置ルールを数値とテストで記録 |
| M5 | Codex Stage Designer Skill | 2〜3週間 | 短いプロットから構造化されたステージ設計データを再現可能な形式で出力 |
| M6 | Unity Stage Builder + Validator | 4〜7週間 | 設計データからSpline、Collider、地形、敵、アイテム、カメラを自動配置・検証・Scene保存 |
| M7 | 自動生成ステージ完成 | 2〜4週間 | 入力したプロットから生成した1ステージを、スタートからゴールまで手動配置なしでプレイできる |

各期間の単純合計は**18〜32週間**。M4/M5の設計作業はM1/M2と一部並行可能。ただし手戻り・Unity環境差・テストで上下するため、計画上の目標は**週10時間で4〜8か月程度**とする。確約ではない。

週5時間なら**8〜16か月程度**を初期目安とし、開発速度が判明した時点で再見積もりする。

## 重要な依存関係

```text
M0
 └─ M1 RailMotor
     └─ M2 自然分岐
         └─ M3 既存ゲームへの統合
             └─ M7 完成ステージ
     └─ M4 移動性能を計測
         └─ M5 Codex Skill ──┐
                              ├─ M6 Builder / Validator ── M7
         M2 分岐仕様 ─────────┘
```

- M4のための**計測方法**はM1から実装してよい。正式な数値確定はM2の分岐を含めて検証する。
- M5のスキル仕様（プロット→ステージ構成）はM1/M2と並行して設計してよいが、**具体的な飛距離や安全距離はM4実測結果を利用**する。
- M6では、従来の生成器を当然の前提にしない。旧StageAutoBuilder等は参照・移行の要否を依存調査で判断する。
- M7で必要な**ゴール・ゲームオーバーの未実装部分**も扱う。これは既存の[ロードマップ](ロードマップ.md)で把握している未完成項目。
- アセット制作と世界観適用はM7の後続フェーズ。ただしColliderと見た目の整合性・カメラ視認性はアート適用後に再検証する。

## 受け入れテスト / 次段階への移行条件

### M0: 既存への影響が見える

- [ ] Git上とローカルの差分を確認し、新規作業用ブランチを用意
- [ ] 旧生成コード、生成済みScene、StageTheme、ランタイムの依存関係を図にする
- [ ] 不要ツールの削除は調査後に別変更として実施（現時点で削除しない）
- [ ] 旧来の生成器を前提にする設計書は、参照資料と新仕様を区別する

### M1: 直線・曲線で安全に移動できる

- [ ] RailState、RailPath、RailMotor、RailCollisionSolverの責務と入出力を確定
- [ ] 独立したテストシーンで床・壁・天井・カーブを検証
- [ ] レールXZ拘束、壁前停止、正常な落下、ジャンプ、坂の基本挙動を検証
- [ ] 失敗ケースを自動または半自動テストとして保存

### M2: 自然分岐が成立する

- [ ] ジャンプで上ルート／歩行で下ルート／落下で下ルート
- [ ] レール接続・遷移区間・切替条件のデータ構造を確定
- [ ] 交差・近接・合流・逆走時のワープやレール往復を検出
- [ ] 分岐が異なるXZへ曲がるケースの実現範囲を決定

### M3: 統合後もゲームが動く

- [ ] MVPを維持してPlayer/Enemyを新Motorへ接続
- [ ] 攻撃・被弾・アイテム接触イベントを検証
- [ ] カメラ追従、ステージ読み込み、死亡・リスポーンを確認
- [ ] 既存挙動との相違は回帰テストに残す

### M4: ステージ設計の物差しがある

- [ ] 移動速度、ジャンプ距離、高度、滞空時間、足場間隔を計測
- [ ] 穴の幅・障害物・頭上クリアランスの安全余裕を定義
- [ ] 「理論上通れる」と「初心者が安定して通れる」を区別

### M5: プロットから機械可読データを作れる

- [ ] `.agents/skills/stage-designer/SKILL.md`（配置は案）と参照ルールを作成
- [ ] 入力: プロット、難易度、長さ、分岐、必須イベントなど（座標手入力を要求しない）
- [ ] 出力: バージョン付き構造データ（YAML/JSONを比較し採用）
- [ ] 不明点の扱い、生成失敗時の修正ループ、乱数シードを仕様化
- [ ] Codexの既存利用枠で動作確認（別途API呼び出しを必須にしない）

### M6: ステージが自動配置される

- [ ] Schema検証、ゲームプレイ制約のValidator、Unity Builderを分離
- [ ] 同一設計データ・生成器バージョン・アセットで同じ結果を再生成できる
- [ ] 床・穴・分岐・Spline・Collider・敵/アイテム・カメラ・スポーン・ゴールを配置
- [ ] 自動検出可能な破綻（未接続、距離不足、衝突など）を報告
- [ ] **自動検証できない項目は未検証と記録**する

### M7: 1ステージを完成させる

- [ ] 日本語のプロットだけで設計データ→Unity Scene生成まで実行
- [ ] オブジェクト手動配置なしでスタート→分岐→ゴールへ到達
- [ ] 死亡/ゲームオーバー/再挑戦/クリアの最低限の流れが成立
- [ ] 人間によるプレイテストで難易度・見通し・遊びやすさを評価
- [ ] 問題があれば「Skillの設計」「Validator」「Builder」「Motor」のどれかに分類して修正

## 見積もりの前提・リスク

- 最大リスク: **M2の自然分岐**と**M6の実ステージ生成**。小さな検証で成立する方式を先に絞る。
- 旧コードが残っていても「流用すれば短縮できる」とは見積もらない。依存調査の結果次第。
- Unityでの実プレイ確認は必要。AIのコードレビューだけで完了判定しない。
- ステージの面白さを数式だけで保証することはできない。数値検証＋プレイテストを併用。
- マイルストーン完了ごとに実績時間・残課題・次の見積もりを更新する。
