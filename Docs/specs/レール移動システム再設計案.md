# レール移動システム再設計案

- 状態: **設計ドラフト v0.1（未実装・未検証）**
- 作成日: 2026-11-08
- 対象: 3DSide / Unity / 2.5Dレールアクション
- 確認対象: GitHub main（2026-10-13のコミット 99b93299 まで）
- 方針: **既存のMVP、ステージ生成、プレイヤー/敵/アイテムのゲーム進行は維持**。レール移動・衝突解決・カメラの境界のみ再設計する。
- この資料は**新実装の仕様候補**。現行コードの動作説明は Docs/knowledge/ を参照。本文中の「案」「要検証」は実装確定事項ではない。

## 1. 目的と背景

がんばれゴエモン でろでろ道中のような、3Dステージ上を横スクロール操作で進む2.5Dアクションを作る。プレイヤーは原則レール中央に拘束される（**原作の詳細挙動は未確認の仮説**）。

現行 SplineMover → CharacterMover → PlayerCharacter / EnemyCharacter では、Spline側の目標XZとCharacterControllerの衝突後XZがずれる。CharacterMover.ApplyToCharacterControllerでは、壁検知後にRevertT()を呼ぶ一方、事前計算したxzMoveを再計算せずMoveへ渡すため、位置と進行値が不一致になる可能性がある。CCの滑り・isGrounded・補正速度・レール切替が相互に依存するのを断ち切る。

**設計目標**
1. キャラクターのXZは常に選択レール上の中央（通常時の横オフセット=0）。壁への衝突でレール外へ押し出されない。
2. 進行方向、ジャンプ、重力、衝突解決を順序立てて再現・テストできる。
3. 道や壁は標準の3D Colliderを使える。ステージ制作を2D/3D二重管理にしない。
4. 敵・アイテム・攻撃・カメラはレール移動の内部実装に依存しない。
5. 原作の操作感を調整可能な数値として保持する。コンテンツ完成を阻害する過剰な汎用化はしない。

**対象外（第一段階）**: 傾く重力方向、ラグドール、押し合う完全物理挙動、複雑な動く床、ネットワーク同期。対応要否は個別に検討する。

## 2. 候補方式と採否

| 方式 | 利点 | 難点 | 現時点 |
|---|---|---|---|
| CharacterController主体 | 地面・坂・段差が標準対応 | 衝突時の滑りでレールから逸脱。再スナップと矛盾 | **第一候補から外す** |
| Rigidbody主体 | 物理相互作用が豊富 | レール拘束・速度と物理の競合 | 不採用寄り |
| Physics2D + 3D描画 | レール座標上の衝突が簡単 | 3D地形Colliderと2D判定の二重管理 | 今回は不採用寄り |
| **独自RailMotor + Physicsクエリ** | レール拘束を座標上保証。ステージは3D Collider | 接地・坂・段差・めり込み解決は自作 | **検証の第一候補** |

**注意**: 独自方式が確定したわけではない。最小検証で複合地形に破綻するなら方式選定へ戻る。Unity PhysicsのCapsuleCast等を利用するので、物理判定をゼロから実装するわけではない。

## 3. 不変条件と座標の責任

### 3.1 状態の唯一の正

~~~text
RailState:
  railId        現在所属するレール
  s             レール始点からの水平進行距離に対応するパラメータ
  worldY        カプセル足元のワールドY
  verticalSpeed Y方向の速度
  grounded      接地判定（検出結果）
~~~

XZ座標を別の可変状態として保持しない。水平投影したレール中心線を C(s) とすると、

~~~text
WorldPosition(state) = ( Cx(s), worldY, Cz(s) )
~~~

※ Splineそのものの3D弧長と、水平(XZ)弧長は坂道で異なる。**sの定義は要検証**。最小検証は平面Splineに限定し、坂道を扱う前に「3D弧長を採るか水平弧長を採るか」を決定する。レールのYはプレイヤーの絶対高さを強制しない。

- RailMotorだけがRailStateを更新する。
- RailPathは進行位置→ワールド位置、接線、終端/接続情報を返す。移動・衝突・演出は知らない。
- RailCollisionSolverは「希望したRailStateまで安全に進めるか」を検査し、許容状態と接触情報を返す。Transformを直接変更しない。
- Scene上のTransformは**確定後の出力**。衝突後に3D座標をレールへスナップする処理を設けない。
- レール切替は位置が近いだけで無条件に行わず、接続関係、進行方向、足場/高さ、ヒステリシスを考慮した**明示的な状態遷移**とする（細部未決）。

## 4. 物理フレームの処理順（草案）

入力をフレーム単位で収集し、移動計算は固定時間刻みで実施する。カメラの描画追従はLateUpdate。プレイヤー/敵は共通のMotorを利用し、入力源のみ分ける。

~~~mermaid
flowchart TD
    A[入力・AI・外力を取得] --> B[現在のRailStateを読む]
    B --> C[重力・ジャンプから希望速度を算出]
    C --> D[候補s・worldYを作る]
    D --> E[RailCollisionSolverで経路全体を検査]
    E --> F{有効な到達状態か}
    F -->|可| G[到達状態を採用]
    F -->|不可| H[衝突直前の到達可能状態を求める]
    H --> G
    G --> I[接地・天井・壁フラグと速度を更新]
    I --> J[RailStateを確定]
    J --> K[Transform / Animationへ反映]
    K --> L[アイテム・敵・攻撃イベントを別系統で評価]
~~~

**重要な設計上の未決定点**: 水平→垂直を分離して解くと坂や角で不自然になる。斜め移動を拘束曲線に沿って連続的に掃引する方式と、水平・垂直を順次解く方式をテストで比較して決定する。壁に当たっても落下は継続できなければならない。

### 衝突計算（候補アルゴリズム）
1. 現在の有効状態から候補状態までのレール上の経路を、曲率・移動距離・カプセル半径に応じて小区間に分割する（一定ステップのみでは高速移動時の保証が不足）。
2. 各小区間についてCapsuleCast等で静的Colliderを検査。移動開始時の重なりはOverlapCapsule等で別途検査する。LayerMask/QueryTriggerInteractionを用途別に指定。
3. 衝突があれば、レール座標(s, worldY)の**有効範囲内**で許容距離を求める。接線方向へ無制限に滑らせない。余裕距離(skin)を設ける。
4. 上昇中に天井へ当たれば上昇速度を停止、壁なら水平進行を停止。床なら接地法線・傾斜を検査する。角や坂道での同時接触は専用ケースとして検証。
5. 重なりから抜ける有効なレール位置が存在しない場合、無理にワールドXZへ押し出さない。最後の安全位置・被ダメージ・リスポーン等のポリシーに委ねる（詳細未決）。

**禁止**: CapsuleCast1回を「曲線経路の厳密な連続衝突判定」とみなすこと。Transformを直接進めてからRevertT()だけ戻すこと。衝突後のXZを後付け補正して壁にめり込ませること。

## 5. 地面・ジャンプ・段差

- ジャンプの可変高さ、コヨーテタイム、入力バッファ、上昇/下降非対称重力、終端速度は現行CharacterMoverの調整値を継承する。
- GroundDetectorは**足元中心付近の支持面**とその法線、接地可能角度を判定する。CharacterController.isGroundedは使用しない。
- 坂: 地面の法線と上限勾配を検討し、地形への追従・下りの離地・壁判定との競合をテストする。
- 段差: 自動ステップアップの必要性を原作観察で判断する。初版は「ジャンプで越える段差」を許容し、自動乗り越えは後回しでもよい。
- 動く床・片側通行床は別フェーズ。固定床テストを通してから追加する。

## 6. レール切替と端

現行RailManagerの「近くにあるレール」「下にあるレール優先」「端で余白を設ける」知見は資産として残すが、現行アルゴリズムをそのまま新方式に流用するとは限らない。

- 同一位置近辺の多層レール（上を飛び越える、下をくぐる）
- 端からのジャンプと落下、端からの直線外挿
- 連結したレールを逆走した際の切替
- カーブの近接点や交差点での誤切替・ワープ防止

これらは仕様を個別に確定してからレールの接続データと切替条件を設計する。**移動中に最近傍レールを毎フレーム強制採用しない**。

## 7. プレイヤー・敵・アイテム・ステージとの境界

| 要素 | 方針 |
|---|---|
| PlayerCharacter / EnemyCharacter | 入力・AI・状態機械を担当。共通RailMotorへ移動要求を渡す。継承依存は縮小を検討 |
| PlayerModel/Presenter・StageModel/Presenter | **MVPの責務は維持**。HP・残機・リスポーン・シーン遷移は別件 |
| 攻撃・被弾 | 移動を塞ぐ地形Colliderと、攻撃判定・イベント判定を分離する |
| アイテム | 接触で取得。Collider/Triggerイベントの発火条件は採用Motorに応じて明示。必要ならOverlap判定を使う |
| ステージ地形 | 3D BoxCollider / 静的MeshColliderを継続使用 |
| 既存Editor生成 | StageGeometryUtility・StageAutoBuilder・Stage1/2Creatorをできるだけ維持。旧レール依存APIをAdapterで置き換える |
| リスポーン | RailStateをSpawnPointから一度に初期化。カメラもそのフレームでスナップ |

新MotorがColliderを持たない場合、OnTriggerEnterの発火を当然視しない。Interaction/HitDetectorの明示的な仕組みを別に定義する。

## 8. カメラ再設計案

現行SplineFollowCameraはSplineMover参照、接線とupの外積による横配置、LateUpdate追従で構成される。新CameraRigは**読み取り専用のRailPose（確定WorldPosition・接線・進行方向・状態）**を受け、Motor実装を参照しない。

- レールの向きがワールドXの正負を跨いでも、撮影側を自動で突然反転しない。カメラ側の撮影サイドを明示状態として持つ。
- カメラの希望位置・注視点・補間を分離し、急カーブ、角、レール切替、画面端の先行注視で検証する。
- ステージ区間のCameraZoneで追従・固定・ボス演出・距離・高さを切り替えられる拡張余地を残す。
- リスポーン・ステージ開始では補間なしのSnap APIを持つ。
- 壁による視界遮蔽の対策、演出切替時間などは別途仕様を決定する。

## 9. 移行計画（現行ゲームを壊さない）

1. **仕様確定**: 直線、カーブ、壁、床、天井、坂、端、分岐について期待結果を決める。
2. **分離した技術検証Sceneを作成**: RailPath + RailState + RailMotor + CollisionSolver を実装。既存ゲームのPlayerCharacterにはまだ接続しない。
3. **CharacterControllerとの比較テスト**: 同じ地形で衝突の正確さ・工数・再現性を比較し、独自Motor採否を決定する。
4. **接続**: 既存PlayerCharacter / EnemyCharacterから新Motorへ入力を渡すAdapterを実装し、戦闘・アイテム・リスポーンと結合テスト。
5. **カメラとステージツール**: 既存APIをAdapter越しに移行。ステージのCreator再生成と既存Sceneの動作検査を実施。
6. **古い移動基盤の削除**: 参照元がなくなったことを確認してから旧SplineMover・CharacterMover等を整理する。**この資料作成段階ではコード削除しない**。

## 10. 最小受け入れテスト

| ID | シーン | 期待結果 |
|---|---|---|
| R01 | 直線・逆走 | レール中央を維持し距離に応じて等速で動く |
| R02 | 90度カーブ・S字 | XZに横ずれせず、曲線をショートカットしない |
| R03 | 直線/カーブの正面・斜め壁 | 壁の手前で停止、逆入力で離脱できる、めり込まない |
| R04 | 天井へのジャンプ | 上昇が停止し、その後正常に落下 |
| R05 | 壁と天井同時接触 | 停止・落下の解決が安定、振動・ワープなし |
| R06 | 坂・段差・床端 | 接地判定の振動がなく、想定の通行可否を守る |
| R07 | レール分岐・近接・多層 | 予期せぬレール吸着・ワープなし |
| R08 | 敵・アイテム・武器Trigger | 地形衝突とゲームイベントが互いに妨げない |
| R09 | 死亡・リスポーン | RailStateとカメラが初期化され、連続再開できる |
| R10 | フレームレート差・高速移動 | すり抜け・速度ムラ・不正な接地なし |

各ケースでRailState、候補位置、衝突ヒット、確定位置、接地フラグを可視化するDebug Gizmoとログを用意する。
